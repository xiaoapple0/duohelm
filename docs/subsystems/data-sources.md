## 要解决的问题

现在 `data.sync` 一次只用一个插件（`SyncParams.plugin_id`，`tasks/sync.py:81`），写入时按主键逐行覆盖（`Transaction.write` 只比较整行，只写新增或变化的行，不删多余的键，`storage/store.py:390-400`），最后同步的数据源说了算；data.md 数据源表里“xtdata 为主、eltdx 备用”只是文字，代码里没有对应的机制。后果：

- xtdata 0.2.2（xiaoapple0/duohelm-plugins#22）修正了 12 只重整转增股票的复权因子，eltdx 对这些仍是错的。最后同步 eltdx，正确的因子就被覆盖回错的；目前只能靠“先 eltdx、后 xtdata”的同步顺序规避
- 复权因子是累乘的（见 [data.md 的标准格式](data.md#标准格式)）：同一只证券的因子一部分来自 A、一部分来自 B，结果是错的，而逐行覆盖正好会造成这种拼接
- 同一只证券的数据来自哪个数据源，快照里没有记录（只有退市日有 `delist_date_quality.source`）

## 数据类别

| 类别 id | 含义 | 对应数据集 | 插件方法 |
|---|---|---|---|
| `securities` | 证券列表和退市日 | `securities`、`delist_date_quality` | `securities`、`lookup_securities` |
| `calendar` | 交易日历 | `calendar` | `trading_calendar` |
| `bars_1d` | 日线（未复权） | `bars_1d` | `bars`（日频） |
| `adj_factors` | 除权事件和复权因子 | `adj_factors` | `adj_factors` |

以后的类别：分钟线、财务数据、ST 状态、指数成分。**只列出，不在这里设计**，做的时候各自补设计。现在的 ST 名单和指数成分快照（见 [data.md](data.md#st-名单和指数成分快照)）不是类别：它们用 `securities` 类别主数据源的名称和 `index_constituents`，规则不变。类别 id 以后可能新增，使用方遇到不认识的 id 要跳过并记日志，不能报错（同枚举新增取值的规则）。

## 配置

- **每个类别一个主数据源**，另可配一个备用数据源（可空）。默认只配主数据源：数据缺了也从主数据源补（重新同步），不隐式引入第二个数据源。备用不能和主数据源是同一个插件
- 主、备数据源都必须是 `ready` 的行情源插件，并且声明提供这个类别（见[插件声明提供的类别](#插件声明提供的类别契约变更单独-pr)）；不满足时保存配置返回 422
- 存放：`plugin-config.db`（`Settings.plugin_config_path`，`settings.py:50`；用户配置，不进任何仓库，不随快照走）里新增表 `data_source_config(category TEXT PRIMARY KEY, primary_plugin TEXT NOT NULL, backup_plugin TEXT, updated_at INTEGER NOT NULL)`，用该库自己的版本迁移新增（`endpoints.py` 的 `_SCHEMA_V1` 之后加一版），不改已有表。接口 `GET`、`PUT /api/data/sources/config`，只读写配置，不触发同步
- **没有配置时**（升级后第一次启动，或使用者没配）：`data.sync` 按现在的行为运行，`plugin_id` 必填，同一个插件作为四个类别的主数据源，没有备用；来源照常记录（见[来源记录](#来源记录)）。**有配置时**：`data.sync` 不再接受 `plugin_id`（传了返回 422，这改变现有 API 行为，见[待确认](#待确认实现时的取舍)），由配置决定
- **定时同步**（`tasks/schedule.py`）：现在启用的规则必须有 `plugin_id`（`schedule.py:185` 的校验，抛 `ScheduleError`）。有配置时，这条校验不再要求 `plugin_id`，触发时读配置，规则里已有的 `plugin_id` 被忽略并在 `plugin_warning` 里提示；没有配置时校验照旧。配置存在期间启用的规则不带 `plugin_id`，之后配置被清空：触发时按“没有配置且没有 `plugin_id`”处理，提示并跳过，不报崩溃。**这些都是需要新写的逻辑，不是沿用现有行为**：`api/schedules.py:52-54` 的 `plugin_warning` 在 `plugin_id` 为空时返回 None，而且只在 GET 时计算；`schedule.py:256`、`:271` 在没有 `plugin_id` 时静默跳过；`schedule.py:297` 触发时把 `plugin_id` 传给 `data.sync`，有配置时会被 422 拒绝。PR 7 要同时改这几处
- **默认值只是建议，由使用者确认**：同步页面和“数据源配置”页可以请求“探测”：对每个 `ready` 的行情源插件调用 `capabilities` 和 `check_connection`（不取数据），列出每个插件声明的类别、连得上与否，并给出建议。建议只按能力判断，不认插件名字：`securities` 类别优先选 `lists_delisted` 与 `exact_delist_date` 都为 True 且连得上的插件；其他类别在声明了该类别且连得上的插件里选，没有唯一合适的就留空等使用者选。**探测不写配置**，使用者确认才保存。平台的默认值永远不覆盖使用者已设的值（测试里预置一个自定义配置，再探测、再升级，值不变）

## 备用数据源的规则

同一个同步任务里，各类别先跑主数据源，再跑备用数据源，全部在一个事务里写入，提交为一个快照。**初版只有这一种方式**：没有“只跑备用”“只跑主数据源”的分阶段同步（原因见[待确认](#待确认实现时的取舍)）。

1. **只补缺，不覆盖**：备用只写“缺失”的部分，主数据源已有的数据（包括快照里已有、来源未知的数据）不动。不依赖同步顺序，备用同步多少次也不会覆盖主数据源
2. **按“类别＋证券”整只补**，不逐行补。**日线没有例外**（见[待确认](#待确认实现时的取舍)）：主数据源有这只证券的日线，哪怕比备用少一段历史，备用也不补那一段，缺的天数由质量报告的 `missing_days` 暴露。理由：2000 年以前两边价格本来就不一致，拼接会在拼缝处造出假的价格跳变
3. **什么算“缺失”**（都以“证券”为单位判断）：

   | 类别 | 缺失 | 不算缺失 |
   |---|---|---|
   | `securities` | 主数据源的证券列表里没有这个代码，备用有（例如 xtdata 没有 000003.SZ）；或主数据源给的退市日是近似值（`exact` 为 False）而备用给出精确的（部分缺失，见[退市日](#退市日并进这套框架)） | 主数据源有，只是两边不一致 |
   | `calendar` | 主数据源没有这个市场的日历（整个市场是一个单位） | 日历里某几天不同：日历是整体，不拼接，不一致写进报告 |
   | `bars_1d` | 见下面“日线的缺失怎么判断” | 主数据源有数据但少一段历史；被入库检查丢掉的行；整个同步窗口都停牌（主数据源返回空）的证券，只要它不是“主数据源从上市日起一行都没有” |
   | `adj_factors` | 主数据源不认识这只证券（对它调用 `lookup_securities` 没有返回，每 100 个一批，沿用扫描的约定） | 主数据源认识这只证券、但没有因子行：这是“没有除权”，不是缺失 |

   因子要靠 `lookup_securities` 判断，是因为空因子既可能是没有除权，也可能是数据源没有这只证券，只看因子行分不出来。**`lookup_securities` 查询失败（`LookupFailedError`）怎么处理**：对**主数据源**，是“不知道”，任务失败（和 `protocols.py:100-103` 的说明一致，也和退市股扫描一致）；对**备用数据源**，这批证券这次不补，记进 `source_fill`，任务不失败（备用不可用的一般规则，见第 7 条）。后一处和 SDK docstring“这次同步失败”不一致，所以契约 PR 里要同步改 `lookup_securities` 的 docstring：写明“失败时平台按调用的上下文决定是否让同步失败”（只改说明文字，不改签名和行为）

   **日线的缺失怎么判断**（增量同步只请求 [start, end]，`tasks/sync.py:328` 附近的 `fetch_bars(session, batch, start, end)`）：
   - 先看快照（基础快照加这次事务里已写的）里这只证券有没有日线：**有**，就不是缺失，不管这次窗口里主数据源返回了什么（整个窗口停牌时主数据源返回空，`protocols.py:122` 停牌日不返回这一行，这是正常的）
   - 快照里没有，并且主数据源在窗口内返回了行：不缺失
   - 快照里没有，窗口内主数据源也返回空：**额外**以 [上市日（未知时 1990-12-19）, end] 向主数据源探测一次（只用来判断，探测到的行不写入，除非和这次的窗口重合）：探测也是空、并且没有被入库检查丢掉的行，才判为缺失，交给备用；探测有数据，说明只是这个窗口停牌，不缺失
   - 备用对判为缺失的证券，请求 [上市日（未知时 1990-12-19）, end] 的整只日线，不受 `start` 限制（和因子总是从 1990-12-19 请求一样）。此后这只证券的来源记为备用，后续同步沿用备用做增量（第 8 条）
4. **被入库检查丢掉的行不算缺失，不从备用补**（维护者第 4 条）：主数据源给了、但被平台入库检查丢掉的行（成交量为 0 的占位行，现在由 `fetch_bars` 丢弃，`tasks/sync.py:663`；以及下面新增的“价格不是有限正数”检查），按“主数据源的数据有问题”处理：记进质量报告的 `rejected_rows`（类别、证券数、行数、样例），这只证券这个类别**不**交给备用。例：xtdata 退市股价格全为 0，这些证券的日线不会从 eltdx 补。**这条的实际后果见[待确认](#待确认实现时的取舍)第 1 条**：主数据源是 xtdata 时，退市股没有日线，幸存者偏差由报告暴露；要有退市股日线，就把 `bars_1d` 的主数据源配成 eltdx（类别是分开配的）
   - **平台必须看得见被丢掉的行，这条才成立**：现在“价格不是有限正数”的行是 xtdata 插件自己丢弃的（见 data.md 的 xtdata 实测结论），平台只看到“没有这只证券的行”，和“主数据源没有”分不开。所以把这条检查搬进平台的入库检查（`fetch_bars` 旁，丢弃并记 `rejected_rows`），插件在平台检查上线之后再停止自己丢弃（顺序反了，0 价行会写进库，见 data.md 已知缺口里 xtdata 一条）。**插件改之前**，插件自己丢弃的行平台看不到，这些证券会被当成缺失、由备用补，与本条相反：这是过渡期的已知偏差
5. **缺失可补，不一致只报告**：两边都有但数值不同，**不自动换数据源**。同步时平台不为了比较去取备用已被主数据源覆盖的证券（太慢，也改变了备用的角色），不一致由 [data.md 的交叉核对](data.md#交叉核对32)（`data.cross_check`，`plugin_a`、`plugin_b` 填某个类别的主、备）报告；界面上提供“用主、备数据源跑一次交叉核对”的入口。同步本身只在退市日上知道不一致，写进 `delist_date_conflicts`（见下）
6. **主数据源不可用时任务失败并报告，不自动整体改用备用**：某个类别的主数据源连接检查没通过、能力检查失败、插件出错，任务失败，不写快照，错误里写明是哪个类别的哪个插件。不提供“失败后换备用”，避免数据今天来自 A、明天来自 B
7. **备用不可用**：主数据源这一轮的数据照常提交，质量报告的 `source_fill` 记 `unavailable` 和原因，任务结果的 `backup_unavailable` 列出类别，任务日志记警告；不让整个任务失败（理由和可撤销见[待确认](#待确认实现时的取舍)）。缺的部分下次同步再补。备用不可用时，`securities` 里已有的、来自备用的精确退市日保留（只要主数据源仍认为这只证券已退市），不被主数据源的近似值覆盖回去
8. **来源归属**（`calendar`、`bars_1d`、`adj_factors` 三个类别）：每只证券每个类别，来源就是写入它的数据源（记录见下）。主数据源处理来源为空或来源是当前主数据源的证券；备用只处理“主数据源没有、快照里也没有任何数据”的证券（新补），和来源已经是当前备用的证券（沿用同一个数据源增量更新，不换人）。**来源是别的数据源的证券，主、备这一轮都不动**，见[换数据源](#换数据源)。**`securities` 类别不按这一条处理**：证券行的名称、上市日（以及 ST 由名称算出的状态）必须每次由主数据源照常更新，否则名称过时会让 ST 判定出错；退市日的规则见[退市日并进这套框架](#退市日并进这套框架)

## 来源记录

新增两个平台自己的数据集（和 `delist_date_quality` 一样不是插件的输出格式，在 `storage/datasets.py` 加定义，随快照保存）：

| 数据集 | 主键 | 列 | 说明 |
|---|---|---|---|
| `data_sources` | `category`、`key` | `category`（String）、`key`（String：证券类别写证券代码，`calendar` 写市场如 `CN`）、`source`（String，插件 id）、`role`（String，`primary` 或 `backup`，写入时这个插件在配置里的角色） | 不分区；每个“类别＋证券”一行，只在来源变化时重写（`Transaction.write` 只写变化的行，重复同步不产生新快照）；没有时间戳（同样的数据得到同样的快照） |
| `source_config` | `category`、`role` | `category`、`role`、`plugin_id`、`plugin_version` | 这个快照写入时每个类别主、备数据源的插件 id 和版本（见[可复现](#可复现)）；没有备用时没有 `backup` 行 |

- **证券行级来源也记在 `data_sources`**（`category = securities`）：记提供这一行（名称、上市日等）的数据源。**`delist_date_quality.source` 的语义改定为“退市日的来源”**，和 `tasks/delist_merge.py:133-146` 的现有行为一致（保留别人的退市日时，`source` 用已有的；否则用这次的）。两者分开记的理由：备用替换了近似退市日时，这一行的名称来自主数据源，退市日来自备用，一个 `source` 列说不清；`delist_date_quality` 保持现状，不改列、不改含义
- **旧数据没有来源**：升级前的快照没有这两个数据集（读取接口按“数据集不存在”处理，同现有规则，不当成空表），升级后第一次同步才创建。**没有 `data_sources` 行的证券就是“来源未知”**，界面和统计里单独一类；不按快照的 note、任务 id 猜，也不回填
- **迁移**：只新增数据集和 `plugin-config.db` 的一张表。不改已有数据集的格式，不重写、不删除、不覆盖任何已入库的数据；旧快照照常能读、能钉住、能回测。没有配置的过渡期同样写这两个数据集（角色全是 `primary`，插件是 `plugin_id` 那个）

## 退市日并进这套框架

退市日归 `securities` 类别，由这个类别的主数据源负责。现在的 [data.md 的“多个数据源的退市日”](data.md#多个数据源的退市日)改为这个类别的主、备规则，只在这里保留一处说明（实现合并后，那一节改写为指向这里，只留旧快照兼容的部分）：

- **主数据源给了证券行就以它为准**，包括在市还是退市。主数据源给的退市日是近似值（`Capabilities.exact_delist_date` 为 False，即 `delist_date_quality.exact` 为 False）时，这个退市日算**部分缺失**：备用对同一只证券给出精确退市日（备用 `exact_delist_date` 为 True，也认为已退市）的，可以只替换 `delist_date` 和 `delist_date_quality`（`exact` 改 True，`source` 记备用），名称、上市日等其他列仍用主数据源的
- **备用不能改在市/退市的判断**：主数据源说在市、备用说已退市，或反过来，**保持主数据源的结论**，只在质量报告的 `delist_date_conflicts` 里记两边的数据源和日期（沿用现有字段，加主、备角色），任务日志记警告，由使用者决定。主数据源是近似的、备用是精确的，也一样不翻转
- 备用有、主数据源证券列表里没有的证券：整行补进来，`exact` 按备用的声明（备用是 eltdx 时为 False）
- **保留“来源未知的行不受保护”**：旧快照里 `source` 为空的行（SDK 0.4.1 之前 eltdx 写的“假精确”和更早的行），备用仍按现有表的“来源未知”规则处理（不受保护，可被覆盖，冲突照记），主数据源照常覆盖；新写入的行都有来源，这条只对旧快照起作用
- 近似值换成精确值只会让退市日更准（通常更晚，回测区间的终点后移，影响同 data.md“对结果的影响”那一条）

**主数据源是精确的（例如 xtdata）时，结果和现在的规则一样**，除了下面清单里标明的情形。**与现在不同的情形清单**（PR 4 的验收按这份清单逐条写测试，P 是主数据源，B 是备用）：

| # | 情形 | 现在 | 新规则 |
|---|---|---|---|
| 1 | P、B 都精确，给出不同的退市日 | 以后同步的为准 | 以 P 为准，与顺序无关 |
| 2 | P、B 都精确，一个说在市、一个说已退市 | 以后同步的为准（任务日志警告） | 以 P 为准，冲突记 `delist_date_conflicts` |
| 3 | 旧快照里精确数据源写的在市行（`exact` 为 null、`source` 是它，过渡期），B 近似说已退市 | 覆盖成已退市，记 `exact_confirmed` 为 false 的冲突 | P 每次同步都重写它列出的证券，已是精确在市，B 不能翻转，记冲突；过渡期的 `exact_confirmed` 不再需要 |
| 4 | P 近似说已退市，B 精确说在市 | 精确的在市覆盖，按在市，记冲突 | 保持已退市，记冲突（备用不能翻转） |
| 5 | P 近似说在市，B 精确说已退市 | 精确的退市日覆盖，按已退市 | 保持在市，记冲突 |

## 换数据源

使用者把某个类别的主数据源从 A 换成 B（或换备用）时（维护者第 1 条）：

- **旧数据保留，并标注来源**：`data_sources` 里这些证券的 `source` 仍是 A，`source_config` 记录写入时的配置。平台**不自动删除，也不自动重新同步**
- **提示风险，建议重新同步**：保存新配置的接口返回“来源变化”的统计：这个类别有多少只证券的来源不是新配置里的主、备数据源，并写明风险：这些证券不会再被增量更新（见[备用数据源的规则](#备用数据源的规则)第 8 条，来源不是当前主、备的证券两边都不动），而且一个类别里混着两个数据源的数据，复权因子混用会算错。同步页面在这个类别上常驻显示“N 只证券来自旧数据源”，质量报告的 `source_fill.other_source` 同样列出（类别、来源、证券数、样例）
- **是否重新同步由使用者决定**：同步任务提供显式参数 `replace_other_source: true`（默认 false，页面上单独确认）：对来源是别的数据源的证券，新数据源取到**非空**数据时整只替换（写入新数据，并给新数据没有的旧键写删除标记，日线和因子都一样），来源改成新数据源；新数据源返回空的证券不替换（空是“不知道”，不能清掉旧数据），记进报告。删除标记不删文件，替换前的快照照常可读、可复现
- **第一次配置时，已有数据来源未知**，按“来源为空”处理：主数据源照常写入（按主键覆盖，和现在一样），**不会删掉来源未知的旧数据里主数据源没有的键**，见[量化正确性](#量化正确性)里的缺口。质量报告的 `source_fill.unknown_source` 记数量，提醒这部分数据的来源没有记录

## 可复现

快照和回测结果简单记下当时的数据源配置（维护者第 2 条）：

- `source_config` 数据集随快照保存，记每个类别主、备数据源的插件 id 和版本（来自插件清单的 `plugin.version`）。配置或插件版本变化时这一行才变化：只升级插件版本也会产生一个很小的新快照；数据没变、版本没变时仍不产生新快照（取舍见[待确认](#待确认实现时的取舍)）

- 哪只证券来自哪个数据源，读 `data_sources`，随快照固定；旧快照里没有就是“来源未知”

## 量化正确性

对 AGENTS.md 红线的影响，逐条：

- **未来函数**：不改变任何因子或日期的因果性。复权因子仍由 SDK `factors_from_events` 按除权日之前的数据计算（有测试守护），备用补的因子也由它计算，且总是从 1990-12-19 请求到 `end`。来源记录和 `source_config` 没有时间戳；备用补缺发生在同步当天，但补的是历史数据本身，不改变“数据在哪一天可用”的判断，ST 和指数成分快照的可用日期规则不变
- **幸存者偏差**：
  - 变好：主数据源没有的退市股（如 000003.SZ）由备用补进证券列表；近似退市日可以被精确值替换
  - 不变坏：备用不能把主数据源的退市翻转成在市，也不能把在市翻转成退市，冲突只报告，不会因为备用的代码表里还有它就让它“复活”。**P 是近似源时例外，见下一条**
  - **有两处不如现在**。第一处：被入库检查丢掉的行不从备用补（维护者决定）。主数据源是 xtdata 时退市股没有日线，现在靠同步 eltdx 补上。要有退市股日线，需要把 `bars_1d` 的主数据源配成能给出价格的数据源；报告的 `rejected_rows` 和 `missing_days` 暴露这一点，不悄悄处理
  - **第二处**：主数据源是近似源（例如 eltdx）、备用是精确源时，“备用不能翻转在市/退市”会让 B（精确）给出的已退市证券被判为在市（情形清单第 5、7a 条）：现在这种情况会采用精确源的退市结论，新规则不会。方向上这是幸存者偏差变坏。冲突记进 `delist_date_conflicts`，不悄悄处理；是否接受见[待确认](#待确认实现时的取舍)第 4 条
- **时间错位**：两个数据源的日期都由插件按 Asia/Shanghai 给出，经同样的入库检查，平台不另做换算。日历按市场整体用一个数据源，不拼接；日线和因子按整只用一个数据源
- **复权累乘（有一个缺口）**：
  - **新补的证券**不混用来源：备用只写快照里没有任何因子行的证券；来源是别的数据源的证券，因子也不被新数据源按键覆盖，只有使用者显式 `replace_other_source` 才整只替换（写入新序列并给旧键写删除标记）
  - **缺口：来源未知的旧数据**。第一次配置时，主数据源按主键覆盖这些证券，但 `Transaction.write` 不删多余的键（`storage/store.py:390-400`）：旧数据里只有 eltdx 有的因子行（主数据源在那些日期没有事件）和日线行（主数据源没有的日期）会留下，完整同步一次也一样。结果是这些证券的因子序列可能一部分来自 xtdata、一部分来自旧的 eltdx，累乘可能不对。**这个缺口不能靠“再同步一次”消除**；设计里的处理是在 `source_fill.unknown_source_leftover` 里报告数量，让使用者知道哪些证券有残留。**“主数据源第一次接管来源未知的证券时，按证券整只替换（给旧键写删除标记）”是一个可选方案，需要维护者决定**，见[待确认](#待确认实现时的取舍)
  - 因子和日线可能来自不同数据源（类别分开配）：因子是比例，由除权事件和除权前收盘价决定，不影响复权公式，但数据源收盘价口径不同时（2000 年以前）会有差异，配置页在选择时提示
- **和 xtdata 0.2.2 因子修正（xiaoapple0/duohelm-plugins#22）的关系**：`adj_factors` 的主数据源配 xtdata、备用配 eltdx 后，xtdata 已有因子行的证券（包括修正的 12 只）都是“主数据源认识”，eltdx 对它们不写；再跑 eltdx 也不会覆盖 xtdata 的因子，不再依赖“先 eltdx、后 xtdata”的顺序。eltdx 只补 xtdata 不认识的证券（例如早年退市的），这些证券 xtdata 本来就没有因子可被覆盖。快照里已有的因子（来源未知）不会被备用覆盖，所以升级前的快照也受保护。**已经被 eltdx 覆盖成错的因子**：xtdata 作为主数据源同步时会按键覆盖它有因子行的日期，但 eltdx 在 xtdata 没有事件的日期留下的因子行不会被删（上面的缺口），所以这 12 只证券是否完全恢复要看有没有残留，由 `unknown_source_leftover` 报告；不要假定一次完整同步就恢复

## 待确认/实现时的取舍

以下是设计时自己定的、维护者在 #99 里没有决定的内容，每条写明能不能撤销。

1. **【需维护者决定】被入库检查丢掉的行不补的实际后果**（来自维护者第 4 条）：主数据源是 xtdata 时，退市股没有日线（xtdata 给的价格全为 0，被丢掉），不从 eltdx 补，幸存者偏差由报告暴露。设计上让使用者把 `bars_1d` 的主数据源单独配成 eltdx 来解决，不给这一条开例外。**可撤销**（改规则，不涉及数据格式）；请维护者确认这个后果符合预期
2. **【需维护者决定】来源未知的旧数据被主数据源第一次接管时，是否按证券整只替换**：现在的设计只按键覆盖，旧数据里主数据源没有的键（例如只有 eltdx 有的因子行）会残留，因子累乘可能混用两个数据源，只靠 `unknown_source_leftover` 报告。可选方案：主数据源第一次接管来源未知的证券时，该证券的因子和日线整只替换（写入主数据源的数据，给旧键写删除标记，只在主数据源返回非空时）。和维护者第 1 条“旧数据保留”的关系：旧快照仍在、仍可读，只在新快照里替换；但这是平台自动改写已入库数据的旧键，第 1 条说的是换主数据源时不自动删除，这里是否算例外，由维护者决定。**可撤销**
3. **【需维护者决定】契约方案**：`Capabilities.categories`（可选字段，`None` 表示没声明）、SDK 版本号 0.4.4、旧插件没声明时按提供四类处理、类别 id 取名（`securities`、`calendar`、`bars_1d`、`adj_factors`）、`lookup_securities` docstring 改说明。需要先认可方向，再开契约 PR，由维护者合并。**可改**。方向已认可，契约 PR（实现拆分第 1 个）按此实现，待维护者合并
4. **【需维护者决定】主数据源是近似源时，备用精确给出的已退市证券会被判为在市**：为了满足维护者第 5 条“备用不能把在市改成退市、也不能把退市改成在市”，新规则在 P 近似说在市、B 精确说已退市时保持在市（情形清单第 5、7a 条），而现在的规则会采用精确源的退市结论。这使幸存者偏差在 P 为近似源（例如只用 eltdx 为主）时比现在更差，只靠 `delist_date_conflicts` 报告。可选方案：对“B 精确说已退市、P 近似说在市”这一种情形允许 B 改为已退市（只改近似源的在市，不改精确源的结论），其余仍不翻转。需要维护者在“严格不翻转”和这个例外之间决定。**可撤销**
5. **有配置时 `data.sync` 收到 `plugin_id` 返回 422**：改变现有 API 行为（现有调用方、定时同步规则里的 `plugin_id` 要迁移；定时规则里的 `plugin_id` 在有配置时被忽略并告警）。**可撤销**（改成忽略并警告）
6. **`replace_other_source` 参数**：换数据源后，使用者显式选择让新数据源整只替换来源是别的数据源的证券（非空才替换，用删除标记，旧快照仍可读）。设计里它是维护者第 1 条“由使用者决定是否重新同步”的落地方式，参数形式和默认值是我定的。**可撤销**（改成不删只写新数据，接受混合）
7. **平台自己做“价格不是有限正数”的入库检查**，并要求 xtdata 插件之后停止自己丢弃：否则平台看不到被丢弃的行，无法区分“被丢掉”和“主数据源没有”。过渡期里插件自己丢弃的行会被当成缺失、由备用补，与第 1 条相反。**可撤销**，但需要插件仓库配合；这是实现第 1 条的前提，不是新决定
8. **配置存放位置**：`plugin-config.db` 里的新表，而不是 `duohelm.db`（任务、定时规则所在）或配置文件。理由：它是用户配置，不随快照走，和用户确认的连接地址放一起。**可撤销**（迁移一次）
9. **日线不设例外**（#99 初稿说“例外在设计里单独写明”）：主数据源有这只证券的日线，备用就不补缺的那一段历史，只在报告里暴露。**可撤销**（以后可以加“主数据源首日晚于上市日”的例外，但要先论证拼缝处的价格口径）
10. **日线缺失的判断多一次探测请求**（窗口内为空、快照里也没有时，向主数据源以 [上市日, end] 探测）：这是为了区分“窗口停牌”和“没有这只证券”。**可撤销**（可以改成只看快照里有没有）
