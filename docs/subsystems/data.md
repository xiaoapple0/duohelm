# 行情与数据

## 职责

- 行情源插件：从外部数据源取数，转换成标准格式
- 平台：校验格式和质量、入库、提供给因子计算和回测

## 标准格式

权威定义：`packages/duohelm-sdk/src/duohelm_sdk/schema.py`。

日频 K 线（`BARS_SCHEMA`）：

| 列 | 类型 | 说明 |
|---|---|---|
| `date` | Date | 交易日 |
| `symbol` | String | 证券代码，A 股用 `600000.SH` / `000001.SZ` / `920000.BJ` 格式（北交所已改用 920 开头的代码） |
| `open` `high` `low` `close` | Float64 | **未复权**价格 |
| `volume` | Float64 | 成交量（股） |
| `amount` | Float64 | 成交额（元） |

复权因子单独存储，在计算时按需应用。原因：前复权价格会随新的除权事件改变历史值，直接存前复权价格会破坏可复现性，也容易引入未来函数。

复权因子（`ADJ_FACTORS_SCHEMA`，SDK 0.2 起）：

| 列 | 类型 | 说明 |
|---|---|---|
| `date` | Date | 除权除息日 |
| `symbol` | String | 证券代码 |
| `factor` | Float64 | **累计后复权比例**，自 `date` 当天起生效，直到下一行；第一行之前视为 1.0 |

- 后复权价 = 未复权价 × factor(t)；以 T 日为基准的前复权价 = 未复权价 × factor(t) / factor(T)
- 因子只能由 `date` 及以前的事件和行情决定，不得用之后的数据归一化
- 计算方法（`duohelm_sdk.adjust.factors_from_events`）：每个事件取除权日**之前**最近的收盘价 P，除权参考价 = (P − 每股派现 + 配股价 × 每股配股数) / (1 + 每股送转 + 每股配股数)，比例 = P / 参考价，按日期累乘。有测试守护：截断某日之后的事件或行情，该日及以前的因子不变

证券列表（`SECURITIES_SCHEMA`，SDK 0.2 起）：

| 列 | 类型 | 说明 |
|---|---|---|
| `symbol` | String | 证券代码，唯一 |
| `name` | String | 名称 |
| `exchange` | String | `SH` / `SZ` / `BJ`，与代码后缀一致 |
| `kind` | String | `stock` / `index` |
| `list_date` | Date | 上市日，未知时为 null |
| `delist_date` | Date | 退市日：摘牌日之前的最后一个交易所交易日（见下），仍在市时为 null |

`delist_date` 按交易日历取摘牌日之前的最后一个交易日，**不是**这只证券最后一根 K 线的日期。退市前停牌的证券（如中国北车：2015 年停牌后换股吸收合并），退市日晚于最后一根 K 线，中间的日子是停牌、不能成交。

拿不到摘牌日的数据源（如 eltdx）在 `Capabilities.exact_delist_date` 里声明为 False（SDK 0.4.1 起），给出的退市日是近似值。平台在数据集 `delist_date_quality` 里逐只记下退市日是否精确，见[存储](#存储m1)下的数据集表。

`exchange` 和 `kind` 以后可能新增取值：使用方遇到不认识的取值要跳过这一行，不能报错（`schema.known_securities()`）。

能直接列出退市证券的数据源（如 xtdata）在 `Capabilities.lists_delisted` 中声明，平台直接取完整名单；不能的（如 eltdx），平台用 `lookup_securities` 扫描代码区间。

## 数据源（M1 决定）

| 角色 | 数据源 | 说明 |
|---|---|---|
| **主数据源** | **MiniQMT（迅投 xtdata）** | 2026-11-25 改定。通过已登录的 MiniQMT 客户端取数；MiniQMT 可以和 DuoHelm 不在同一台机器上，连接地址由本机配置文件指定。xtquant 用 MiniQMT 自带的或迅投官方发布的版本，不用 PyPI 上的同名包 |
| **备用、交叉核对** | **eltdx 3.3.5** | 通达信协议的 Python 库。xtdata 不可用时备用；补全 xtdata 缺失的退市证券；交叉核对日线、除权和交易日 |

两个行情源插件都放在插件仓库 `duohelm-plugins`，平台本身不依赖 xtquant 或 eltdx。

### 行情数据只供本人使用

- 通过 MiniQMT 和 eltdx 取得的行情数据，**只供维护者本人研究使用**，不得分发、转售或提供给他人
- **录制的行情数据（测试用的回放文件等）只放在本机，不进任何仓库**。duohelm 和 duohelm-plugins 都是公开仓库；录制文件**只能**放在本地的 `.local-data/` 目录（被 `.gitignore` 忽略），推送前按插件仓库 AGENTS.md 的命令检查整个 git 历史，结果必须为空
- `$DUOHELM_HOME/data` 下的行情数据只在本机，不同步、不上传
- **MiniQMT 的实际地址不进任何仓库**：插件清单只声明默认值 `127.0.0.1:58610`，实际地址写在不提交的本机配置文件里

### MiniQMT（xtdata）

- 需要一台运行并登录着 MiniQMT 的机器。同步任务开始时先检查 MiniQMT 是否连得上，连不上就报错并提示打开它
- 当前使用**普通版**（投研版的“板块成分股变动历史”“ST 变更历史”等特色数据不可用），暂不升级
- 使用条款以券商和迅投的协议为准，M6 模拟盘、M7 实盘之前需要确认

#### 实测结论（xtquant 250807 官方包，普通版，2026-11-25）

| 项目 | 结果 | 平台的处理 |
|---|---|---|
| **日期** | `get_market_data_ex` 的日期字符串按**运行机器的本机时区**格式化：测试机在美东时区，所有日期整体早一天（宁德时代上市日显示为 2018-06-10，星期日） | 日期一律由 `time` 字段的毫秒时间戳按 **Asia/Shanghai** 换算，不使用日期字符串。插件测试在非东八区时区下断言已知日期；主仓库 CI 有 `TZ=America/New_York` 的测试任务 |
| 日线最早年份 | 从上市首日开始：上证指数 1990-12-19，平安银行 1991-01-05，北交所 920000.BJ 2020-12-23 | 全量导入不设起始年份 |
| **退市证券** | `download_history_contracts()` 后，“过期沪深A股”板块有 313 只；合约信息有名称、上市日、退市日；完整日线可取。**早年退市的不全**：PT金田A（000003.SZ，2002）、*ST石化A（000013.SZ，2004）完全不存在，2001–2004 年总共只有 8 只 | 证券列表以 xtdata 为主，再用 eltdx 扫描代码区间补全；两边不一致的写进质量报告 |
| 除权数据 | `get_divid_factors`：`interest` 每股派息（元，税前）、`stockBonus` 每股送股、`stockGift` 每股转增、`allotNum` 每股配股、`allotPrice` 配股价、`gugai` 股改标记、`dr` 除权系数（6 位小数）。单位已用公开分红核对（茅台 2024-06-19 每股 30.876 元，平安银行 2024-06-14 每股 0.719 元） | 换算为 `EX_EVENTS_SCHEMA` 后用 `factors_from_events` 计算 |
| 等比复权 | 与 SDK `factors_from_events` 是同一种方法：6 只样本股的单次比例与 `dr` 的相对差中位数在 5e-7 到 1.6e-4 之间（`dr` 只有 6 位小数）；个别早年事件差异较大，最大是茅台 2006-05-24 的 0.65% | 用 SDK 计算因子；单次比例与 `dr` 相差超过 0.1% 的事件写进质量报告 |
| 停牌 | 历史停牌日没有这一行（`fill_data=False`），返回行的 `suspendFlag` 全是 0；`fill_data=True` 会把停牌日补成整行；另有少量成交量为 0 的占位行（平安银行 13 行，多在 1991–1997 年） | 只用 `fill_data=False`；丢弃成交量为 0 的行 |
| 交易日历 | `get_trading_dates("SH")` 与 `("SZ")` 完全相同（1990-12-19 起，2024 年 242 天）；深市日历实际上就是沪市日历，没有 1991 年深市的周六交易日，而 xtdata 自己的平安银行日线里有 11 根 1991 年周六的 K 线 | `CN` 日历取两市并集；1992 年以前不在日历里的 K 线写进质量报告 |
| 历史指数成分 | `get_stock_list_in_sector` 的历史日期参数在普通版上不生效（返回当前成分）；“板块成分股变动历史”需要投研版 | 从 M1 起每天保存成分快照，之前的时期写进已知缺口 |
| ST 数据 | `get_his_st_data` 读的是 MiniQMT 所在机器的本地文件，远程调用为空；“ST 变更历史”在普通版上为空 | 从 M1 起每天保存 ST 名单快照（#11） |
| 成交量单位 | 平安银行（股票）的 `volume` 单位为**手**；其他证券类型（指数、ETF、北交所）待逐类核对 | 插件按证券类型分别核对单位并有测试，不统一乘 100 |

**与 eltdx 的交叉核对（平安银行）**：xtdata 8546 根，eltdx 8499 根，**xtdata 净多 47 根**（xtdata 独有 48 根，eltdx 独有 1 根）。xtdata 独有的 48 根中：11 根是 1991-04-03 之前的周六记录（9 根开高低收相同、成交量很小，2 根成交量为 0）；11 根是成交量为 0 的占位行；26 根是 eltdx 缺少的 1992–1996 年交易日。eltdx 多出 1 根（1991-09-30）。两边都有的日期，收盘价不一致的天数：1991–1999 年 163/2142，2000–2015 年 24/3710，**2016 年以来 0/2646**（成交量按手、股换算后同样全部一致）。2000 年以前的数据可信度存疑，两边不一致的写进质量报告。

### eltdx（备用）

#### 许可限制

eltdx 的许可是“非商业学习与数据研究”：

- 只允许个人学习、数据接口与格式研究及非商业用途
- 禁止把 eltdx、衍生作品**或通过它获取的数据**用于商业活动、付费服务、生产服务、转售、营利性数据服务、**自动化交易服务**
- 访问第三方服务器须自行遵守相关法律法规和服务协议

对本项目的影响：

- M1–M5（行情、股票池、因子、研究、回测）属于个人非商业研究，在许可范围内
- **M7 实盘之前必须重新确认许可**：用 eltdx 获取的数据驱动自动下单，可能落入“自动化交易服务”的禁止范围。M6 模拟盘开始前也应先确认
- 项目将来如果开放给其他用户、提供服务或涉及任何收费，都必须先重新评估数据源

#### 实测结论（eltdx 3.3.5，2026-11-25）

| 项目 | 结果 | 平台的处理 |
|---|---|---|
| 日线最早年份 | 上证指数从 1990-12-19 开始，个股从上市首日开始（平安银行 1991-04-03）；北交所现用 920 开头的代码，历史从 2020-12-23 开始 | 首次全量导入从上市首日开始，不设起始年份 |
| 退市股票 | 普通 K 线接口对退市股返回空；专用的退市日线接口能取到完整的未复权历史（测试的 8 只都能取到，最早的退市于 2002 年）。**代码表只有在市股票，没有退市名单** | 首次导入时扫描 A 股代码区间，发现退市股；之后每天对比代码表，发现新退市的股票 |
| 复权 | 服务器的复权价是“未复权价 × 系数 + 偏移”的线性变换，前复权早期价格会出现负数（平安银行最早为 −3.51） | 不使用服务器复权价。平台存未复权价，并根据除权除息记录在本地计算按比例的复权因子 |
| 停牌 | 历史停牌日**没有这一行**；当前停牌的股票当天会多出一根成交量为 0、价格等于前收盘价的占位 K 线 | 入库时丢弃成交量为 0 的行；“某个交易日没有这一行”即表示当天不可交易 |
| 交易日历 | 没有专门的接口，eltdx 自己也是用基准指数的日线推出来的。1991 年深市周六开市，上证指数推出的日历里没有这些日子；2000 年以后沪深两市完全一致 | 按交易所分别用指数日线推出日历：上海用 `sh000001`，深圳和北京用 `sz399001` |
| 历史指数成分 | 只有当前成分名单和纳入日期，**没有调出记录**，无法得到历史成分 | 从 M1 开始每天保存成分快照；之前的历史成分属于已知缺口（见下） |

## 存储（M1）

源码：`packages/duohelm/src/duohelm/storage/`。数据根目录是 `$DUOHELM_HOME/data`（默认 `~/.duohelm/data`）：

```
data/
  files/<数据集>/<分区>/<sha256>.parquet   数据文件，按内容命名，写好后从不修改
  manifests/<快照 id>.json                每个快照一份清单
  catalog.db                              快照、当前快照指针、钉住的快照、退市股扫描记录（SQLite）
```

| 数据集 | 格式 | 主键 | 分区 |
|---|---|---|---|
| `bars_1d` | `BARS_SCHEMA` | symbol、date | 按 date 的年份 |
| `adj_factors` | `ADJ_FACTORS_SCHEMA` | symbol、date | 不分区 |
| `securities` | `SECURITIES_SCHEMA` | symbol | 不分区 |
| `calendar` | market、date | market、date | 不分区 |
| `delist_date_quality` | symbol、exact | symbol | 不分区 |
| `st_daily` | date、symbol、name、status | date、symbol | 按 date 的年份 |
| `index_members_daily` | date、index、symbol | date、index、symbol | 按 date 的年份 |
| `quality_report` | key、report | key | 不分区 |

`st_daily` 和 `index_members_daily` 是每日快照数据集，见[ST 名单和指数成分快照](#st-名单和指数成分快照)。

`delist_date_quality` 是平台自己的数据集，不是插件的输出格式。每只证券一行，和 `securities` 在同一个事务里写入：`exact` 为 True 表示退市日精确，为 False 表示近似值（数据源的 `exact_delist_date` 为 False），为 null 表示仍在市。快照里没有某只证券的行（例如 SDK 0.4.1 之前同步的快照），表示“不知道”，不能当成精确。

读取规则：拿 `securities` 左连接这个数据集时，“没有行”和“仍在市”都得到 null，要靠 `delist_date` 区分。**`delist_date` 不为空且 `exact` 为 True，才算精确**；`delist_date` 不为空而 `exact` 为 null，是“不知道”。True 只表示数据源没有声明是近似值：还没升级到 SDK 0.4.1 的插件同步出的行也是 True。eltdx 升级前同步过的，升级后再同步一次就会改为 False（扫描路径每次都会重新查询全部退市股）

### 只新增文件

- 每次写入生成新的 Parquet 文件，已有的文件从不修改。修改和删除都通过追加新文件完成
- 每个文件多一列 `_deleted`：为 True 的行是**删除标记**，表示这个主键的数据作废（其余列为 null）
- 读取时按清单里的文件顺序合并：同一个主键以最后出现的为准，最后去掉删除标记
- 写入前先和当前快照比对，只写入新增或变化的行；删除标记也只写给当前存在的主键。所以重复写入同样的数据不会产生新文件，也不会产生新快照
- 写文件时先写临时文件、落盘（fsync），再按内容的 sha256 改名。同样内容的文件只存一份
- 分区列必须是主键的一部分，这样同一个主键的所有版本都在同一个分区里

### 快照

- 清单是规范化的 JSON（键排序、无多余空白），按顺序列出每个数据集生效的文件及其 sha256、行数和分区。**清单的 sha256 就是快照 id**：内容相同，id 相同，与写入的机器和数据集的写入顺序无关（前提是 polars 版本相同，Parquet 编码一致）
- `catalog.db` 记录每个快照的父快照、创建时间、产生它的任务和统计，以及当前快照指针
- 提交用乐观锁：切换当前快照时，指针必须仍等于写入开始时的快照，否则抛 `SnapshotConflictError`，这次写入的新文件被删除
- 研究和回测记录所用的快照 id，并把它**钉住**（`catalog.pin`），之后按同一份清单读取，结果可以复现

### 整理与清理

- **整理**（`compact`）：把一个数据集每个分区的多个文件合并成一个，同时消化删除标记。生效数据不变，产生一个新快照；旧快照照样能读
- **清理**（`gc`）：保留当前快照、钉住的快照和 `keep_days` 天内创建的快照，其余快照的清单删除并标记为已清理；不被任何保留快照引用、且修改时间早于 `min_file_age_s` 的数据文件删除（默认 24 小时，给正在写入、尚未提交的事务留出时间）

### 退市股扫描记录

不能直接列出退市证券的数据源（`Capabilities.lists_delisted` 为 False），`data.sync` 用 `lookup_securities` 扫描代码区间（源码：`packages/duohelm/src/duohelm/tasks/delisted.py`，#30）。

扫描区间（含两端，不含 B 股和北交所旧代码），共 16999 个代码：

| 交易所 | 代码 |
|---|---|
| 沪市 | 600000–605999（主板）、688000–689999（科创板） |
| 深市 | 000001–004999（主板，含原中小板）、300000–302999（创业板，含 302 开头的新代码） |
| 北交所 | 920000–920999（现用代码，1000 个） |

B 股和北交所 43、83、87 开头的旧代码不扫，见[已知缺口](#已知缺口)。

第一次同步（扫描记录为空）要查询区间内所有不在代码表里的代码，每 100 个一批，最多约 170 批。每批耗时取决于数据源，没有用真实数据源实测（未核对），所以这里不给总耗时。之后的同步只重扫到期的“没找到”的代码。

扫描记录在 `catalog.db` 的 `security_scan` 表，**按数据源分开**（一个数据源没有某个代码，不代表别的数据源也没有），不随快照变化。目录库 v1 的旧表改名为 `security_scan_v1` 保留。每行的 `scanned_at` 是这个代码最近一次被查询的时间（#36、#37）。目录库 v3 把 v2 的所有“没找到”行的 `scanned_at` 置 0，即查询时间未知，视为已过期，下一次同步就重扫。流程：

1. 代码表里的证券记为“扫到过”。代码表为空，或证券数不到这个数据源扫到过的代码数的一半，任务失败：多半是数据源一时出错，往下走会把在市证券当成不在代码表里去查询
2. 还没扫过的代码，每 100 个一批查询；每批结束就记下有没有找到和查询时间。任务失败或取消后，下次从没扫过的代码接着扫。**“没找到”的代码按重扫间隔重新查询**（#36、#37）：距上次查询超过 `rescan_days`（同步参数，默认 7 天；0 表示每次同步都重查）的，和没扫过的代码一起，在这次同步里按同样的每 100 个一批、每批落库的方式查询。批次落库后查询时间更新，所以重扫中途失败或取消，下次只接着查还没重扫的。重扫查到了，转为“扫到过”，进入第 3 步的重新查询。这解决两种情况：数据源一时对存在的代码返回空（之前会被永久记为没有）；两次同步之间上市又退市、代码之前已记为没找到的股票
3. 扫到过、但现在不在代码表里的代码，**每次同步都重新查询**，取得最新的上市、退市日期；上次还在代码表里、这次不在了的（新退市）也在其中。之前扫到过、这次查不到的，任务失败：查不到是“不知道”，不能当成没有这只证券。如果确认数据源已经永久去掉了这个代码，维护者在停止服务后手工删除 `security_scan` 里对应的行（`DELETE FROM security_scan WHERE source = '<插件 id>' AND symbol = '<代码>'`），之后的同步就不再查询它
4. `lookup_securities` 返回了没有查询的代码，任务失败

扫描完成后才取日线，没扫完的名单不会写进快照。任务结果里的 `scanned`、`rescanned`、`rechecked` 是这次新扫描的代码数、重扫“没找到”的代码数、重新查询扫到过的退市股的代码数。

元数据（任务等）仍在 `$DUOHELM_HOME/duohelm.db`；行情的目录库单独放在 `data/catalog.db`，两者的表结构版本互不影响。

## 读取接口（M1）

源码：核心库 `packages/duohelm/src/duohelm/storage/reader.py`（`MarketReader`），HTTP 接口 `packages/duohelm/src/duohelm/api/data.py`（前缀 `/api/data`，#46）。API 只是核心库的薄封装。

**只读**：读取不写任何数据、不产生快照、不推进当前快照。每个接口都可以用 `snapshot` 参数读指定的旧快照；不传就读当前快照。一次请求内只解析一次快照 id，之后全部用这个 id 读取，同步任务在请求中途提交新快照不会让一次响应混合两个快照。响应里总带着实际读取的 `snapshot` id。

### 接口

| 接口 | 参数 | 返回 |
|---|---|---|
| `GET /api/data/snapshots` | `limit`（1–200，默认 50） | `current`（当前快照 id，还没有任何快照时为 null）和快照列表（新的在前，不含已清理的）：id、parent、created_at、task_id、note、stats、is_current |
| `GET /api/data/snapshots/current` | 无 | 当前快照的元数据；还没有快照时 404 |
| `GET /api/data/securities` | `snapshot`、`symbol`（精确匹配）、`name_prefix`（名称前缀，按字面匹配，不是正则）、`kind`、`limit`（1–500，默认 100）、`offset` | `total`（筛选后的总数）和当前页，按代码排序 |
| `GET /api/data/securities/{symbol}/bars` | `snapshot`、`start`、`end`、`adjust`（`none` / `hfq` / `qfq`，默认 `none`）、`base_date` | 某只证券某区间的日线，按日期升序 |
| `GET /api/data/coverage` | `snapshot`、`kind`、`limit`（1–500，默认 100）、`offset` | 每只证券的覆盖统计，按代码排序，含 `total` |

日期参数（`start`、`end`、`base_date`）只接受 ISO 日期 `YYYY-MM-DD`，含义是**北京时间的交易日**，不做任何时区换算，也不接受时间戳或带时间的字符串；非法值返回 422。`start`、`end` 含两端，不传表示不设下限、上限；`start` 晚于 `end` 返回 422。`snapshot` 必须是 64 位小写十六进制的快照 id，格式不对返回 422（它会拼进文件路径，所以先校验格式）。

### 404 和空结果的区别

- **404**（带说明）：快照不存在或已被清理、还没有任何快照、快照里没有所需的数据集、证券不存在。**不会用空表代替**，因为“没有数据”和“没取到数据”对研究的意义完全不同
  - 日线需要 `securities`、`bars_1d`；复权（`hfq`、`qfq`）还需要 `adj_factors`：数据集整个不存在时是“不知道有没有除权”，不能当成因子为 1；数据集存在、但这只证券没有因子行，才表示没有除权事件，因子为 1
  - 覆盖统计需要 `securities`、`bars_1d`、`calendar`（`market = CN`）
- **200 且 `bars` 为空列表、`empty` 为 true**：证券存在（在 `securities` 里），但所读区间内没有日线（区间在上市前、退市后，或整段停牌）。响应里仍带 `symbol`、`snapshot`、`last_bar_date`（这只证券在这个快照里的最后一根日线，没有任何日线时为 null）。`empty` 是明确的标记，前端据此显示“区间内无数据”，不要用 `bars.length` 猜
- 证券列表筛选没有匹配项：200，`total` 为 0，`items` 为空。这是筛选结果，不是缺数据

### 复权

只复用 `duohelm_sdk.adjust.adjust_bars`，平台不另写复权逻辑。价格列（open、high、low、close）调整，`volume` 和 `amount` 不调整。

- `none`：返回入库的未复权价格
- `hfq`：后复权，价格 × factor(t)
- `qfq`：以基准日 T 为基准的前复权，价格 × factor(t) / factor(T)

**前复权基准日规则**（未来函数红线）：

1. 不传 `base_date` 时，基准日是**所读区间的最后一天**，即返回的日线里最后一根的日期
2. 传了 `base_date` 时，不能晚于所读区间的结束（`end`；没有传 `end` 时是这只证券的最后一根日线）。晚了返回 422：基准日之后的因子不属于“所读区间”，用了就是拿区间之后的信息改写区间内的价格
3. 基准日也不能晚于这只证券在这个快照里的最后一个日线日期（该证券没有任何日线时不检查）
4. 读取因子时多加了一道上限：只取 `date` 不晚于 `end` 的行。这是冗余保护：`adjust_bars` 本身按日期向后查找因子，区间之后的因子行即使读进来也不会影响区间内的价格，去掉这道上限不会让任何测试变红。真正保证“基准日及之前的前复权价格不受之后因子影响”的是规则 1–3 的基准日约束，以及 SDK 因子计算的因果性（有测试守护：基准日之后的因子变化不改变基准日及之前的前复权价格）
5. 基准日早于 `start` 是允许的：价格 × factor(t) / factor(T)，T 在区间之前
6. `adjust` 不是 `qfq` 时传 `base_date` 返回 422，避免参数被悄悄忽略

响应里带 `adjust` 和实际使用的 `base_date`（`qfq` 且区间为空且没有传入时为 null）。因为基准日随区间变，同一天的前复权价格在不同的 `end` 下不同，这是前复权的性质；需要稳定的价格序列时用后复权，或固定 `base_date`。

### 覆盖统计

对每只证券（`securities` 里的全部，加上 `bars_1d` 里有但 `securities` 里没有的代码，`name`、`kind` 为 null）：

| 字段 | 含义 |
|---|---|
| `first_date`、`last_date` | 这个快照里这只证券日线的首末日期；没有日线时为 null |
| `bar_count` | 日线根数 |
| `expected_days` | CN 交易日历在 `first_date` 到 `last_date`（含两端）之间的交易日数；没有日线时为 null |
| `missing_days` | `expected_days` 减去落在交易日历上的日线根数，即按日历应有而缺失的天数；没有日线时为 null |
| `off_calendar_bars` | 首末之间不在交易日历上的日线根数（数据或日历有问题的信号），正常为 0 |

**停牌日也算缺失**：同步入库时不保存停牌日的行（见数据源实测结论），所以覆盖统计分不出“停牌”和“漏数据”，`missing_days` 是两者之和。它是进一步检查的线索，不是数据错误的判定；退市前长期停牌的证券，`last_date` 之后到退市日之间的日子不计入（统计只到 `last_date`）。计算用 polars 向量化完成（分组聚合加对交易日历的二分查找），不逐只证券循环。

### K 线查看页面（#47）

源码：`web/src/pages/kline/`，接口类型 `web/src/api/data.ts`（手写，与 `api/data.py` 的响应一致，M1 改为从 OpenAPI 生成后删除）。页面路径 `/kline`，只调上面的读取接口。

- 选证券（按名称前缀或代码搜索）、起止日期、复权方式（`none` / `hfq` / `qfq`，`qfq` 用后端默认基准日，即区间最后一根）；画 K 线（红涨绿跌）和成交量，全部用 SVG，没有图表库依赖
- 日期按北京时间的交易日处理：默认区间的“今天”用 `Intl` 以 `Asia/Shanghai` 换算，日期始终是 `YYYY-MM-DD` 字符串，日期运算用 UTC 日历，不经过浏览器本机时区
- **三种结果分开显示**：
  - 后端 404 或网络错误：写明“未知”（没取到数据，不等于没有数据），带后端的说明
  - 后端 422：参数不合法，原样显示后端的说明
  - 200 且 `empty` 为 true：写明“区间内没有数据”，附这只证券在快照里最后一根日线的日期
- 缺失值：`open` / `high` / `low` / `close` / `volume` 为 null 时不当成 0 画。价格缺任何一项的那一天不画蜡烛，在底部标“缺失”；成交量缺失不画柱；悬浮信息里写“缺失”。价格坐标范围只用非空值计算
- 一次查看里的所有请求都用第一个响应里的 `snapshot` 固定读同一个快照，不会混合两个快照

**停牌和除权日的标注（后端没有直接给出，页面用已有接口推导，有局限）**

读取接口目前不返回交易日历，也不返回复权因子，页面不能直接读“日历里有、K 线里没有”和“因子变化日”：

- 停牌或缺数据的日子：用上证指数（`000001.SH`，同一快照、同一区间）有日线的日子当作参考日历；参考日历有、这只证券没有日线的日子标为“停牌或缺数据”。入库时不保存停牌日（见上），停牌和漏数据分不出来，所以不能叫“停牌”。只标 `list_date`（未知时用区间内第一根日线）到 `delist_date`（没有时用这只证券在快照里最后一根日线）之间的日子，上市前、退市后不标
  - 参考指数读不到（404 等）、或证券信息（`/securities?symbol=`）读不到时，这项标注写“未知”，不换别的边界去标，也不会当成“没有”
  - 没有 `delist_date` 的证券，最后一根日线之后到区间结束的日子无法判断（可能正在停牌，也可能还没同步），页面写明“某日起是否停牌未知”，不标
  - 参考日历是代理，不是 CN 交易日历：指数自己缺的日子发现不了；没有 `list_date` 的证券，区间起点之前就缺的日子，区间开头发现不了
- 除权日：同一区间再读一次另一种复权方式（当前是 `none` 时读 `hfq`，否则读 `none`），逐日取收盘价之比，比值相对前一根日线变化超过 1e-6 的那根日线标为“除权”。除权日当天停牌时，标记落在之后的第一根日线。区间第一根日线无法判断是否除权。复权数据集不存在（404）时除权日写“未知”，而不是“没有除权”

已知缺口：读取接口应直接提供交易日历和复权因子（含除权日），页面才能做出精确标注（#76，见下面的“已知缺口”）。

### 覆盖情况页面（#48）

源码：`web/src/pages/coverage/`（`load.ts` 取数和汇总，`CoveragePage.tsx` 界面，`text.ts` 文字），接口类型在 `web/src/api/data.ts`。页面路径 `/coverage`，只调读取接口（`/coverage`、`/securities`、`/snapshots`），不新增后端接口。

- **取全**：覆盖统计每页最多 500 条，页面逐页串行取完所有分页再汇总（后端每页都全量扫描日线，并发会同时做多次全量扫描；打开一次页面的代价约为页数 × 全量扫描），汇总和筛选的“全部”都是全量，不是第一页。第一页不指定快照，拿到快照 id 后其余分页、证券信息都固定读这个快照；任何一页的快照 id 不一致就整体报错。取到的条数与 `total` 不一致时，页面顶部写明“只取到 N / total 条，汇总不完整”
- **每只证券**：代码、名称、交易所、种类、状态、首日、末日、K 线数、应有天数、缺失天数、非交易日日线数；每列可排序（空值排在最后），可按代码或名称、交易所、种类、在市/退市筛选，也可只看有缺失的、只看无日线的。表格上方的汇总（按交易所、证券种类、在市/退市：证券数、无日线数、有缺失数）不随筛选变化
- **缺失天数**：页面写明“按交易日历应有而库里没有的日子，停牌日也算缺失，分不出停牌和漏数据”，见[覆盖统计](#覆盖统计)
- **快照**：显示快照 id、创建时间（按 `Asia/Shanghai` 显示，不依赖浏览器本机时区），以及它是否仍是当前快照。创建时间来自 `/snapshots`（最多取最近 200 个）；读取失败或快照已不在列表里时写“未知”
- **三种结果分开显示**：
  - 覆盖统计 404（还没有快照、快照被清理、缺 `securities`/`bars_1d`/`calendar`）：写“未知”，带后端说明，提示先同步
  - 网络错误、服务器错误：写“未知：没有取到覆盖统计”，不显示任何汇总，不当成 0 或“没有数据”
  - 200 且没有任何证券：写“快照读取成功，但里面没有任何证券”
  - 重新读取失败时不再显示上一次的结果
- **覆盖统计接口没有的字段，页面从 `/securities` 补**：覆盖统计只给代码、名称、种类，没有交易所和退市日。交易所取自 `/securities` 的 `exchange`；在市/退市用 `delist_date`：有退市日且不晚于今天（北京日期）为已退市，没有退市日算在市。`/securities` 读不到、或这只证券不在 `securities` 里（只在日线里出现的代码）、或 `exchange` 为空时，交易所和状态写“未知”，汇总里单独一行“未知”，不归到任何一类。接口缺口见 #80
- 局限：
  - 部分数据源的退市日是近似值，没有退市日也可能是数据源拿不到，所以“在市”只表示“证券信息里没有退市日”，见[已知缺口](#已知缺口)
  - 种类和交易所的汇总是前端算的，要全量取数（约 5000 多只证券，11 页左右）；证券量更大时应由接口提供汇总（见已知缺口）
  - 没有自动化测试（`web/` 没有测试框架），也没有在浏览器里实测，只通过了类型检查和构建

## 同步任务（M1）

源码：`packages/duohelm/src/duohelm/tasks/sync.py`。任务类型 `data.sync`，参数：

| 参数 | 说明 |
|---|---|
| `plugin_id` | 行情源插件的 id，插件状态必须是 `ready`、kind 为 `datasource` |
| `start` | 默认 1990-12-19（上证指数第一个交易日） |
| `indexes` | 要保存成分快照的指数代码列表，默认 `000300.SH`、`000905.SH`、`000852.SH`、`000016.SH`、`399006.SZ`、`000688.SH`（沪深300、中证500、中证1000、上证50、创业板指、科创50）。传空列表则不保存成分快照 |
| `rescan_days` | 退市股扫描：“没找到”的代码距上次查询超过这么多天就重扫，默认 7，范围 0 到 3650，不接受 inf、nan；0 表示每次同步都重查所有没找到的代码（扫描区间共 16999 个代码，每次重扫的是其中没找到的部分，绝大多数代码都没有证券，所以 0 时接近整个区间，较慢）。只对 `lists_delisted` 为 False 的数据源有效 |
| `end` | 默认为最近一个已收盘的日子：北京时间 15:30 之后是今天，之前是昨天（按 UTC+8 换算，不依赖本机时区；不判断是不是交易日，非交易日没有日线）。显式传入还没收盘的日子，任务失败：盘中的日线不是最终值，不能进快照。不能早于 `start` |

流程：

1. 用 `session_for` 在隔离进程里启动插件，传入用户在插件页确认过的连接地址和 network。地址没确认时插件报 `EndpointNotConfiguredError`，任务失败，提示去插件页确认
2. 调用 `check_connection`（插件实现了的话），`ok=False` 时任务直接失败，不下载任何数据。插件给的说明会进任务日志和结果，其中用户确认的地址替换成 `<endpoint id 的地址>`
3. 检查 `capabilities`：必须支持 CN 市场和日线
4. 取完整的证券列表，用 `check_securities` 检查，只保留认识的交易所和证券种类。`lists_delisted` 为 True 的数据源直接取 `include_delisted=True`；为 False 的，取代码表后做退市股扫描（见[退市股扫描记录](#退市股扫描记录)）。只用在市股票的列表回测过去会有幸存者偏差
5. 取 [start, end] 的交易日历
6. 对上市日不晚于 `end`、退市日不早于 `start` 的证券，每 50 只一批取未复权日线（[start, end]）和复权因子：
   - **复权因子总是从 1990-12-19 请求到 `end`**，不管 `start` 是哪天。因子是累计值，第一行之前视为 1.0；只按 [start, end] 请求时，`start` 之前最后一次除权的因子拿不到，区间开头的 K 线会按 1.0 复权
   - 日线用 `BARS_SCHEMA` 检查格式，复权因子用 `check_adj_factors` 检查；出现没有请求的证券、或日期不在请求的区间内，任务失败
   - **丢弃成交量为 0 的行**（停牌占位 K 线），结果里记丢弃的行数。“某个交易日没有这一行”即表示当天不可交易
   - **成交量为空时任务失败**：空是“不知道”，不能当成 0 按停牌丢掉
7. 证券列表、退市日精确与否（`delist_date_quality`）、日历、日线、复权因子，ST 名单和指数成分的每日快照（见下节）、入库质量报告（见[入库质量报告](#入库质量报告)），在**一个事务**里写入，提交为一个快照，快照记下任务 id。数据没有变化时不产生新快照（`snapshot_id` 为空）

出错时：

- 任何一步失败，事务中止，已写的数据文件删除，当前快照不变
- 插件超时（`timeout`）、子进程意外退出（`crashed`）、提交时当前快照已被别的写入改变，按 `RetryableError` 自动重试；其他错误（插件异常、返回值不合格、地址没确认、连接检查没通过等）直接失败
- 取消：后台线程每秒检查一次取消请求，收到后结束插件子进程；提交前再检查一次，被取消的任务不留下快照

入库前只做格式和范围检查；质量检查见[入库质量报告](#入库质量报告)。两个数据源的交叉核对见下面的“交叉核对”一节（#32），同步页面见下节“同步页面”；也可以通过任务 API 创建（`POST /api/tasks`）。

### 同步页面

源码：`web/src/pages/sync/`，路径 `/sync`（菜单“数据同步”），界面文字在 `text.ts`（#33）。页面只调用现有接口，不新增后端接口。

- **手动同步**：选择行情源（只列 kind 为 `datasource` 的插件；状态不是 `ready` 的不可选）、起止日期，提交 `data.sync`（`POST /api/tasks`，`dedupe_key` 为 `manual:data.sync`：同一时刻只允许一个手动同步，重复点击返回 409 并提示）。只要有未结束（排队或运行中）的 data.sync 任务（不论手动还是定时提交、不论页面正在看哪个任务），“开始同步”就禁用；页面每 3 秒查一次，正在看别的任务时提示并可一键回到运行中的任务
- **日期**：起始默认 1990-12-19。结束默认是最近一个已收盘的日子，规则和后端一致：北京时间 15:30 之后是今天，之前是昨天；“今天”按 Asia/Shanghai 换算，不用浏览器本机时区。结束晚于它、或早于起始时页面直接拒绝，不提交（后端也会拒绝）。结束日期等于默认值时照样显式传入
- **连接地址没确认**：所选插件有 `state` 不是 `confirmed` 的 endpoint，或 network 为 `needs_approval` 时，页面提示并给出“去插件页确认”的链接，同时禁用“开始同步”，因为插件在确认前连不上
- **进度、日志、结果**：页面显示最近一个 `data.sync` 任务（不论是手动还是定时提交的），每 2 秒刷新到结束；刷新页面后仍能看到。进度条、状态、取消和重试用任务中心的组件（`tasks/TaskBits.tsx`），日志的拉取、去重、轮询是共用的 `tasks/useTaskFeed.ts`，日志显示是共用的 `tasks/TaskLogs.tsx`，任务中心的详情抽屉和本页用的是同一份。结果显示快照 id（为空表示数据没有变化、没有产生新快照）、各数据集写入的行数、丢弃的成交量为 0 的行数，以及结果里的其他字段（没有专门位置的字段原样显示 JSON）
- **定时同步**：显示和修改 `/api/schedules/data-sync`（见 [tasks.md](tasks.md) 的“定时触发”）：开关（默认关闭）、行情源、触发时间（北京时间，必须晚于 15:30，页面先检查，后端也会返回 422）；只提交改动过的字段。显示下次触发时间、上次处理日期、`plugin_warning`、`needs_full_sync`、`state_error`。“上次运行状态和错误”来自最近一个 `dedupe_key` 为 `schedule:data.sync` 的任务（在最近 200 个 `data.sync` 任务里找）：定时触发被去重跳过、当天判定为非交易日时不产生任务，此时只有上次处理日期。读取任务列表失败时，这一项显示“未知”，规则表单照常可用。这是后端接口的缺口，跟踪见 #71。规则和最近任务分开加载：任务结束只重取最近任务，不重取规则，不会覆盖表单里没保存的修改；规则只在首次加载、保存成功、点“刷新”或“重试”成功时以服务端为准；刷新或加载规则失败时，不显示旧值的可编辑表单，显示“加载失败，当前规则未知”和重试按钮；定时面板只在未结束的任务变为已结束时才重取最近任务

### ST 名单和指数成分快照

源码：`packages/duohelm/src/duohelm/tasks/snapshots.py`（#43）。xtdata 普通版和 eltdx 都拿不到历史 ST 状态和历史指数成分，只能从第一次运行起**每天保存快照**，晚一天就永远少一天的 point-in-time 数据。不改 SDK 契约：ST 由证券列表里的名称判定，成分用已有的 `DataSourcePlugin.index_constituents`。

| 数据集 | 内容 |
|---|---|
| `st_daily` | 快照日期 `date` 那天的 ST 和“ST 状态未知”的证券：`symbol`、`name`（当时的名称，未知时为 null）、`status`（`st` 或 `unknown`） |
| `index_members_daily` | 快照日期那天指数 `index` 的成分 `symbol` |

**什么时候写**

- **只在交易日 15:30 之后运行时写**：快照日期 = 最近已收盘的日子（`last_closed_day`，按 Asia/Shanghai 换算，不依赖本机时区），并且它必须是运行当天（北京时间）、且是 `CN` 日历里的交易日。名单是运行那一刻的名单，只有收盘后才能代表这个交易日；开盘前运行（如周一 09:00 运行，最近已收盘的日子是周日；周二 09:00 运行，最近已收盘的日子是周一但名称已是周二的）、周末和节假日运行都**不写**，也就不会用新的名单改写前一个交易日已经写好的快照
- 同步的 `end` 也必须等于最近已收盘的日子（默认 `end`）。`end` 早于它（回补历史）**不写**：今天的名单不能当成过去的名单
- 没有写时，任务结果的 `snapshot_skipped` 写明原因
- 与证券列表、日线等在同一个事务里提交；事务失败则快照也不写
- 同一天重复同步：这一天的行以最后一次为准（名单里已经没有的证券会被删除标记作废），其他日期不动

**ST 判定**

- 范围：`kind` 为 `stock`、`list_date` 不晚于快照日期（或未知）、`delist_date` 为空或晚于快照日期的证券，也就是在市股票
- 规则：名称去掉所有空白（含全角空格）、转大写后，以 `ST`、`*ST`、`SST`、`S*ST` 开头，且后面不是英文字母（排除 `STAR` 之类）。名称中间含 ST（如 `中ST股份`）不算
- 名称为空的在市股票，ST 状态是**未知**，写入 `st_daily`，`status` 为 `unknown`（`name` 为 null），任务结果的 `st_unknown_names` 记下数量。在市股票的名称全部为空时，整个 ST 快照不写（`st_snapshot_failed`）
- 读取规则：某个日期**有任何 `st_daily` 行**才表示这一天有快照。有快照的日子里，`status = 'st'` 的是 ST，`status = 'unknown'` 的**不知道**（不能当非 ST），不在 `st_daily` 里的在市股票才是非 ST。没有快照的日子是“不知道”，不是“没有 ST”
- 同一天重复同步时，名称这次拿不到的股票，已有的行保持不变（不改成 `unknown`、不作废）：之前知道的比现在不知道的好

**指数成分**

- 对每个指数调用 `index_constituents(index, 快照日期, 快照日期)`，只保留快照日期时已经调入（`in_date` 为空或不晚于它）、尚未调出（`out_date` 为空或晚于它）的成分
- **`out_date` 的解释**：调出生效日，即第一天不再是成分；`in_date` 是调入生效日，当天已是成分；`out_date` 为空表示仍在指数中（SDK 文档只写了“仍在指数中则为 null”，这里补上非空时的含义）。已有的插件实现：eltdx 只有当前成分，`out_date` 全为 null，`in_date` 为纳入日期，所以快照就是当前成分；xtdata 插件不在本机的插件仓库里，没有核对
- **读取失败是“未知”，不是“空”**：方法报错（包括 `NotImplementedError`：行情源要满足 `DataSourcePlugin`，方法必须存在，不支持成分时抛这个错）、返回格式不对、成分里有空的证券代码、或返回的成分为空，这个指数当天都不写任何行，原因记进任务结果的 `index_snapshot_failed`（指数代码到原因）和日志；其他指数和整个同步不受影响。超时、子进程崩溃、取消仍按上面“出错时”的规则让任务失败或重试
- 读取规则：某个日期某个指数**有行**才表示这一天有这个指数的快照
- 同一天重复同步：这次成功读取的指数，当天的行以这次为准；**这次读取失败的指数，它已有的行不变**；这次 `indexes` 里没有的指数，当天已有的行不动

已知缺口见下面的“已知缺口”一节（#50、#51、#52、#54）。

## 交叉核对（#32）

源码：`packages/duohelm/src/duohelm/tasks/cross_check.py`。任务类型 `data.cross_check`，**只读**：不写任何数据集、不产生快照，结果只放在任务结果里。对同一区间、同一批证券，比较两个行情源插件的未复权日线（OHLCV）和复权因子，用来发现单个数据源的错误（漏数据、复权错、日期错位）。

| 参数 | 说明 |
|---|---|
| `plugin_a`、`plugin_b` | 两个行情源插件的 id，不能相同。结果里的 a、b 分别指它们 |
| `symbols` | 要核对的证券。不传表示两个数据源证券列表的交集（取在区间内可能有行情的证券，列表里是否含退市证券按各自的 `lists_delisted`）；不在交集里的代码记进 `only_listed_in_a`、`only_listed_in_b`（样例加总数），这只是列表差异，不能直接当成漏数据（`lists_delisted` 为 False 的数据源列表里没有退市证券）。股票池（M2）实现后可以展开成这个列表传入 |
| `start`、`end` | `start` 必填；`end` 默认和 `data.sync` 一样是最近一个已收盘的日子，传入还没收盘的日子任务失败 |
| `price_tolerance` | 开高低收的相对差异阈值，默认 0.001：\|a-b\| / max(\|a\|,\|b\|) 超过才算差异 |
| `volume_tolerance` | 成交量的相对差异阈值，默认 0.01 |
| `factor_tolerance` | 复权因子的相对差异阈值，默认 0.001 |
| `max_examples` | 每一类差异最多保留的样例数，默认 100，上限 10000；总数不受限制 |

**比较什么**

- **日线**：两边都丢弃成交量为 0 的行（停牌占位，同 `data.sync` 入库时的处理；但成交量为空时 `data.sync` 直接判为不合格，这里不能失败，见 `partial`）。按 (证券, 日期) 对齐：
  - 只在一边出现的日期：`only_in_a`、`only_in_b`（漏数据、日期错位）
  - 两边都有的日期，开、高、低、收、成交量各自比较，超过阈值记 `bar_mismatch`（`field` 指明字段）。某个字段至少有一边为空（NaN 按空处理）时不比较，次数记进 `unknown_fields`，不当成相同也不当成不同；这样的行不计入 `bars_consistent`（两边五个字段都知道、都在阈值内的行数）
  - 成交量按 SDK 契约比较，契约规定单位是股，**不做单位换算**。某个证券两边都有成交量的行（至少 5 行）里，90% 以上 a/b 接近 100 或 0.01（误差 2% 内），判定有一边的单位不是股（例如手），记一条 `volume_unit_mismatch`（整个证券一条，`note` 写明比值），该证券不再逐日列成交量差异。这是插件违反契约，不是数据差异，参见 xiaoapple0/duohelm-plugins#3（eltdx 指数成交量的单位）
- **复权因子**：总是从 1990-12-19 请求到 `end`（同 `data.sync`）。因子是累计值的阶梯函数，在两边所有除权日上比较各自生效的因子（第一行之前为 1.0），超过阈值记 `factor_mismatch`；`note` 说明这一天是否只有一边有除权记录。除权日早于 `start` 的差异也会列出，因为累计值会带进区间
- 不比较成交额、证券列表和退市日（退市日的近似值见已知缺口）

**读取失败是“未知”，不是“没有差异”**

- 数据源整体不可用（连接检查没通过、能力检查失败、没传 `symbols` 时证券列表失败、插件启动失败）：记进 `sources`（`ok` 为 False 和原因）；某一批证券的日线或复权因子读取失败、返回格式不合格、含没请求的证券或区间外的日期：这一批的证券在这个数据源上是未知，记进 `unknown_symbols`（样例加总数 `unknown_symbols_total`），不参与比较，也不会出现在差异里
- `status`：`compared`（所有证券都比较了，且没有字段为空）、`partial`（有证券未知，或 `unknown_fields` 不为空：有字段为空没有比较）、`unknown`（一个证券也没比较成，或没传 `symbols` 又无法确定证券范围）。**两个数据源都正常、只是证券列表的交集为空时，`status` 也是 `unknown`**（没有比较任何证券，不能说“一致”）。`complete` 就是 `status == compared`。只有 `complete` 为 True 才能说“核对完成”；`partial` 和 `unknown` 里没列出的差异不代表没有差异
- 取消照常取消；插件报错、超时都记为未知，任务本身不自动重试（`max_attempts` 为 1）。参数不合格、插件不存在或不是行情源、`end` 未收盘，任务失败

**结果的大小**：样例名额按 kind 分配，`bar_mismatch` 再按字段分配（开、高、低、收、成交量各自最多 `max_examples` 条，开盘价的差异占不满别的字段的名额）；每个名额里保留最先遇到的样例（证券每 50 只一批，批内按代码排序、再按日期，批与批之间保持传入顺序；不传 `symbols` 时整体按代码排序），输出时统一按 kind、证券、日期、字段排序。`counts` 记每类差异的总数（`bar_mismatch` 另按字段拆分，如 `bar_mismatch.close`），`top_symbols` 是差异最多的证券，`symbols_with_differences` 是有差异的证券总数；`examples_truncated` 为 True 表示样例被截断。

## 入库质量报告

源码：`packages/duohelm/src/duohelm/tasks/quality.py`（检查）、`packages/duohelm/src/duohelm/api/data.py`（接口）。#31。

`data.sync` 在同一个事务里生成质量报告，写入 `quality_report` 数据集（一行，`key` 为 `sync`，`report` 是 JSON），**随快照保存**。`SyncResult.quality` 给出各项检查的状态。

- **只报告，不阻止提交**：有问题也照常提交快照。哪些问题要阻止，由维护者决定，待决定项见 #72，决定之前保持现状
- **检查范围是这次同步取到的数据**（[start, end] 内的日线，从 1990-12-19 起的复权因子），不是整个快照；增量同步的报告只覆盖新取的那一段，报告里记了插件 id，以及 start、end：它们是日历里实际覆盖到的第一个和最后一个交易日（请求区间内），不是请求的自然日（区间内没有交易日时为 null）。每次同步覆盖上一次的报告
- 报告不含时间戳：同样的数据得到同样的报告，所以重复同步不会因为报告产生新快照；报告变了（比如覆盖到的交易日区间变了）会产生新快照。节假日、周末触发（请求的 end 落在非交易日）而数据没变时，覆盖到的交易日不变，报告不变，不产生新快照（见 tasks.md 的定时同步）
- 状态有三种：`ok`、`issues`、`unavailable`（无法检查，写明原因）。**`unavailable` 不是 `ok`**
- 早于 #31 的快照没有质量报告：接口返回 404，不是“没有问题”

| 检查 | 内容 |
|---|---|
| `ohlc` | 入库的日线（成交量不为 0）：价格缺失（null 或 NaN）、价格不为正、`high < max(open, close)`、`low > min(open, close)`，各类问题的行数、涉及的证券数、最多 20 个样例。价格缺失或非正的行不再判断高低价 |
| `calendar_dates` | K 线日期不在交易日历里的行数、证券数、样例 |
| `adj_factor_jumps` | 复权因子的每个跳变（比例不为 1 的行，第一行与 1.0 比）应有同一证券同一天的除权除息记录；报告“因子跳变没有事件”和“事件没有因子”的数量和样例。**目前平台拿不到除权除息记录**（数据源接口没有这一项），所以这一项总是 `unavailable`，原因写“数据源没有提供除权除息记录”；有了事件数据（`EX_EVENTS_SCHEMA`）后，由 `QualityCollector(ex_events=...)` 传入，逻辑已有测试 |
| `missing_days` | 每只证券缺失的交易日数：应有的交易日是 [max(start, 上市日), min(end, 退市日)] 内的交易日。成交量为 0 的占位行是已知的停牌，已扣除，只记总数（`placeholder_total`、`symbols_with_placeholder`）。**停牌信息拿不到**：数据源不提供停牌日列表，没有 K 线又没有占位行的日子可能是停牌也可能是缺数据，无法区分，都计入 `missing`；报告里 `suspension` 为 `unknown`。所以停牌多的证券会显得缺得多，不能把 `missing` 直接当成数据缺陷。`per_symbol` **只列出有缺失的证券**（`missing > 0`），同时记总数（`symbols_with_missing`，全部证券数见报告的 `symbols`），报告大小不随正常证券增长。**退市日不精确的证券**（`delist_date_quality.exact` 为 False 或未知，如 eltdx）：它们的退市日是最后一根有成交的 K 线的日期，是下界，应有的交易日截到那里，之后的缺口看不到，缺失天数可能少算；`per_symbol` 里这样的证券带 `delist_date_approximate: true`，总数记在 `symbols_with_approximate_delist_date`（没有缺失的也计入） |

读取接口（只读）：`GET /api/data/snapshots/{snapshot_id}/quality-report`，返回该快照的报告 JSON；快照不存在、id 格式不对、快照没有报告都返回 404。

**界面**：这次不做前端页面。界面上查看质量报告由 #33（同步页面）或后续处理，接口已就绪。

## 黄金数据集

“黄金数据集”覆盖行情数据链路（插件输出 → `data.sync` 入库 → 读取 → 复权），用来在改动前后比对结果；提交正文和 PR 说明都写明原因（见 docs/code-standards.md 验收标准第 5 条）。它是否作为 AGENTS.md 阶段 3 所说的黄金数据集，由维护者决定（见跟踪 issue #49）。分两层，范围不同、运行方式不同。

### 第一层：构造数据（提交到仓库，CI 运行）

测试：`packages/duohelm/tests/test_golden_market_data.py`。输入和期望值都写在这个文件里，不依赖任何外部数据。

- **输入**：一个测试用的行情源插件（夹具），在隔离进程里经完整的 `data.sync`（插件 → 检查 → 入库 → 快照）写入快照，再从快照读出数据，用 SDK 的 `adjust_bars` 计算前、后复权价。插件的复权因子由 SDK 的 `factors_from_events` 根据事件和原始日线计算，和真实插件的做法一致
- **覆盖的情形**（共 10 只证券、10 个交易日，跨 2023、2024 两个年度分区）：

  | 情形 | 说明 |
  |---|---|
  | 指数，无事件 | 不应出现因子 |
  | 派现 | 每股派现 |
  | 送转 | 每股送转股数（10 转 5） |
  | 配股 | 每股配股数和配股价 |
  | 跨年多次除权 | 一次在 2023 年，一次在 2024 年，因子累乘 |
  | 停牌缺行 + 占位行 + 复牌日除权 | 停牌日没有行，其中一天有成交量为 0 的占位行；除权参考的是除权日之前最近的收盘价 |
  | 成交量为 0 的占位行（非停牌） | 年初的一行，被丢弃 |
  | 新股上市首日 | 上市前没有行；上市前的除权事件不产生因子 |
  | 退市股（含退市前停牌） | 退市日（摘牌日之前的最后一个交易日）晚于最后一根 K 线，中间是停牌 |
  | 退市日早于同步区间的退市股；上市日晚于同步区间的新股 | 只出现在证券列表里，不取日线 |

- **断言**：入库的日线行（含按年份分区的行数）、丢弃的占位行数、每个数据集的写入行数、复权因子、前复权和后复权价、交易日历、证券列表（上市日、退市日）和 `delist_date_quality`
- **期望值怎么来**：
  - 复权因子：按本文“标准格式”里的公式**手算**，写成分数（如 `Fraction(20, 19)`），注释里写计算过程。不运行被测代码生成期望值
  - 复权价：重点行手算成分数写在常量里；此外对**每一行**，用一个只有几行的、不依赖 SDK 的纯 Python 实现（按手算因子的阶梯函数逐行相乘，用分数运算）逐行核对
  - 其余（行数、丢弃数、日历、退市日）由输入数据的构造直接数出来
  - 数据是编的，价格取得整齐，让手算结果可以一眼验证（例如派现后的后复权价恰好等于除权前的收盘价）

### 第二层：本地录制数据（只在本机运行）

测试：`packages/duohelm/tests/test_golden_local_data.py`，带 `local_data` 标记。

- 读取 `.local-data/` 下插件录制的真实数据（见[行情数据只供本人使用](#行情数据只供本人使用)），目录位置可用环境变量 `DUOHELM_LOCAL_DATA` 指定。录制数据**只在本机，不进仓库**
- 默认不运行（`pyproject.toml` 的 `addopts` 带 `-m "not local_data"`）；运行：`uv run pytest -m local_data`。CI 不运行。录制目录不存在时整体跳过；**录制文件存在、却缺少某次调用或字段时，测试失败**，不跳过
- **只断言公开可查的事实**，不把录制数据的内容复制进仓库：宁德时代、浦发银行、茅台、平安银行的上市日，宁德时代首根日线的日期（由时间戳按 Asia/Shanghai 换算），上证指数 1990-12-19 是交易日历的第一天，茅台 2024-06-19 每股派现 30.876 元、平安银行 2024-06-14 每股派现 0.719 元
- 当前只能读 xtdata 的录制文件。它按调用回放，不是 DuoHelm 的快照格式，所以没有走 `data.sync`；复权因子的数值没有公开可查的标准答案，不在这一层断言

### 什么时候更新

- 黄金数据集的结果变了，必须在提交正文和 PR 说明里写**为什么变**（见 docs/code-standards.md 验收标准第 5 条），以及新的期望值是怎么独立得出的。不能运行改动后的代码，把输出粘贴成新的期望值
- 新发现一类数据问题（又一种停牌方式、新的除权形式），在第一层加一只构造的证券，并写明它对应哪个真实案例
- 数据源的实测结论（见上文）有变化时，检查第二层的断言是否仍然成立

## 已知缺口

- **读取接口没有交易日历和复权因子**（#76）：K 线查看页面只能用上证指数当参考日历推导“停牌或缺数据”的日子，用两种复权收盘价之比推导除权日，有局限（见[K 线查看页面](#k-线查看页面47)）。需要读取接口直接提供两者
- **覆盖统计接口没有交易所、退市日和汇总**（#80）：覆盖情况页面（#48）要同时请求 `/securities` 并在前端合并、全量取数后在前端汇总；证券量大时代价高：后端 `coverage()` 每个请求都全量读 `bars_1d` 再切片，页面逐页串行读取，打开一次的代价约为页数 × 全量扫描。需要接口直接提供交易所、退市日，以及按交易所、种类、在市/退市的汇总。页面里与接口缺口相关的未知项见[覆盖情况页面](#覆盖情况页面48)
- 存储、快照和同步任务已实现。入库时做格式和范围检查，并丢弃停牌占位行；质量报告已实现（#31，只报告，阻止规则待决定 #72，复权跳变因没有除权除息记录无法检查，停牌日未知）；交叉核对（#32）见[交叉核对](#交叉核对32)
- **eltdx 的退市日是近似值**：eltdx 拿不到摘牌日（退市 K 线、F10 基础信息和发行上市信息、公告列表都试过），只能给出最后一根有成交的 K 线的日期，是 SDK 口径的下界；退市前长期停牌的证券会偏早。同步时记为近似值（`delist_date_quality.exact` 为 False，xiaoapple0/duohelm-plugins#7）。用 xtdata 的摘牌日修正近似退市日，由 xiaoapple0/duohelm-plugins#4 跟踪（修复方向 (b)），交叉核对不比较证券列表和退市日，不做这件事；近似值在质量报告里的展示见[入库质量报告](#入库质量报告)：缺失交易日一项给退市日不精确的证券加标注，缺失天数可能少算（#31）。回测怎样处理近似的退市日，在设计回测成交规则时决定
- **退市股扫描的缺口**（`lists_delisted` 为 False 的数据源，如 eltdx）：
  - B 股（沪市 900 开头、深市 200 开头）不扫，这些代码上的退市股发现不了（#35、#69）。原因：平台目前只支持 A 股，B 股的币种和成交规则都没有建模。影响：已退市的 B 股不会出现在证券列表里；平台不回测 B 股，对 A 股的回测结果没有影响
  - 北交所旧代码（43、83、87 开头）不扫，这些代码上的退市股发现不了（#35、#70）。北交所已把旧代码换成 920 开头的新代码，换码日期未核对，见 #70。不扫的原因：
    1. 920 新代码的历史从 2020-12-23 开始；同时扫旧代码，同一家公司会出现两份证券，换码日还会出现一笔假的退市（旧代码“退市”，其实公司还在，用新代码交易），而平台不合并新旧代码的历史
    2. 用 `.BJ` 后缀查询 43/83/87 号段，数据源可能返回只在新三板挂牌、不属于北交所的证券
    3. 这些证券可能拉低 `MIN_LISTED_RATIO` 的比例（代码表里没有它们，却被记为扫到过），导致之后每次同步都报 `ScanError`
    影响：换码前已退市的北交所公司，在旧代码上的历史缺失，回测有幸存者偏差；这部分没有量化，见 #70
  - 重扫间隔内发现不了的证券（#56）：数据源一时对存在的代码返回空、或股票在两次同步之间上市又退市而代码之前已记为“没找到”时，最长要等 `rescan_days`（默认 7 天）加一次同步间隔才会被重扫发现。这只影响发现的时间：发现后能取到它的完整历史日线，不会丢历史。但在发现之前做的回测不含这只证券，有幸存者偏差，发现之后要重跑。`lookup_securities` 不区分“没有这个代码”和“查询失败”，这是 SDK 契约，没有改
  - 每次同步都要重新查询所有扫到过的退市股；eltdx 每只要取一次完整历史，退市股多时耗时较长（#38）
- **历史指数成分和历史 ST 状态**：xtdata 普通版和 eltdx 都不提供。`data.sync` 每天保存 ST 名单和指数成分的快照（#43，见[ST 名单和指数成分快照](#st-名单和指数成分快照)），但只从第一次运行开始；同步漏跑的日子没有快照，不回填（#52）；之前的时期没有 point-in-time 数据，用指数股票池回测会有幸存者偏差（#11）。M2 的股票池先做全 A 股加条件筛选
- **ST 快照靠名称判定，是近似的**（#50）：名称更新可能晚于实际的 ST 实施日；退市整理期、北交所的其他风险警示标记不单独识别
- **指数成分快照依赖插件填写的 `in_date`、`out_date`**（#51）：插件给的是当前成分时，快照就是当前成分；xtdata 插件的实现没有核对
- **快照可能提前一天反映变化**（#54）：快照在交易日 15:30 之后到午夜之间运行，数据源可能在 T 日晚上就把名称（加 ST、摘帽）或指数成分改成 T+1 生效的值，T 日的快照会提前反映。没有限制时间窗口
- **漏跑的交易日没有 ST 和指数成分快照，不回填**（#52）：快照只在交易日 15:30 之后运行的同步里写
- **早年退市证券**：xtdata 缺少部分 2001–2004 年退市的股票，靠 eltdx 扫描补全；两边都没有的无法发现
- **2000 年以前的日线**：xtdata 与 eltdx 存在不一致（收盘价、成交量、个别交易日），可信度存疑
- xtdata（C 扩展连接 MiniQMT）和 eltdx（Rust 原生代码）的连接都不经过 Python socket，Python 层的网络白名单管不到它们。对它们来说，清单里的网络权限只是声明，用户的确认只约束 Python 层的连接：平台只把用户确认过的 MiniQMT 地址交给插件，没确认时 `endpoint("miniqmt")` 报错，xtdata 不会去连（#27）；但这靠插件按 `endpoint()` 取地址，xtquant 本身不受拦截；eltdx 的连接由 Rust 代码发起，确认 network 列表之前同样不受拦截。操作系统层的隔离见 #7
- 停牌后才摘牌的证券、换股吸收合并的证券：最后一根 K 线之后到退市日之间一直停牌，持仓无法卖出；换股合并的持仓按换股比例转成存续公司股票，而不是按退市清零或按最后价格变现。回测要在 M5 专门处理，M1 只保证退市日按上面的定义给出
